# How I Fall — технический план Unity-основы

Статус: план реализации, без изменения игровой логики.

## 0. Ограничения и решение по текущему проекту

- Проект уже работает как Unity-прототип. Основная сцена для VN — `Assets/HowIFall/Scenes/VNPrototype.unity`.
- Существующие `GameState`, `SaveManager`, `SettingsManager`, `VNDialogueController` и ScriptableObject-данные не переименовывать и не заменять.
- План рассчитан на постепенное расширение: сначала сохраняются текущие типизированные поля и ссылки на ассеты, затем при необходимости добавляется более универсальная модель состояния.
- `docs/story/` остаётся источником сценарного канона. Unity хранит исполняемое представление сцены.
- На MVP не нужен отдельный парсер Markdown/JSON. Сценарий фиксируется в Markdown, а небольшая демо-сцена собирается через существующие ScriptableObject вручную.

## 1. Архитектура проекта

### 1.1. Папки

Сохраняем текущую структуру `Assets/HowIFall` и расширяем её только по мере необходимости:

```text
Assets/HowIFall/
  Art/
    Backgrounds/
    Characters/
    UI/
  Audio/
    Music/
    SFX/
  Data/
    Dialogues/       # DialogueSceneData и registry
    Characters/      # добавить, когда появится единый каталог персонажей
    Variables/       # добавить только при переходе к data-driven состоянию
  Prefabs/           # переиспользуемые VN UI и персонажи
  Scenes/
    MainMenu.unity
    VNPrototype.unity
  Scripts/
    Audio/
    Core/
    Save/
    Settings/
    UI/
    VN/
  Editor/             # валидаторы и инструменты только для Unity Editor
```

Сценарная часть вне `Assets`:

```text
docs/story/
  scenes/            # сцены в Markdown
  characters/        # персонажи и их ограничения
  mechanics/         # переменные и правила механик
  routes/            # ветки и условия маршрутов
```

### 1.2. Слои

1. **Данные контента** — ScriptableObject-сцены, строки, выборы, ссылки на ассеты.
2. **Состояние прохождения** — текущая сцена/строка, флаги, числовые переменные, отношения.
3. **Исполнение VN** — переход по строкам, показ фона/персонажа, выбор и переход на следующую сцену.
4. **UI** — диалоговое окно, выборы, backlog, quick menu, save/load и настройки.
5. **Инфраструктура** — сцены Unity, аудио, сохранение в `Application.persistentDataPath`, загрузка ассетов.

Поток данных:

```text
Markdown-сцена -> DialogueSceneData -> VNDialogueController
                                         |
                                         v
                              GameState / StoryState
                                         |
                                         v
                                    SaveManager
```

### 1.3. Системы и классы

| Система | Ответственность | Основные классы |
|---|---|---|
| Состояние игры | Хранит текущую сцену, строку, переменные, флаги и отношения | `GameState` (уже есть), в будущем `StoryState` как сериализуемый слой данных |
| Поток сцен | Старт новой игры, продолжение, переход `MainMenu` ↔ VN | `SceneFlowManager` (уже есть) |
| Диалоговый контент | Описывает сцену, строки, выборы и следующий переход | `DialogueSceneData`, `DialogueLine`, `DialogueChoice`, `DialogueSceneRegistry` (уже есть) |
| Исполнитель диалога | Показывает текущую строку, принимает ввод, переключает строки и выборы | `VNDialogueController` (уже есть) |
| Backlog/история | Записывает показанные реплики и выводит их отдельным экраном | `DialogueBacklog`, `DialogueBacklogEntry` (уже есть) |
| Выборы | Проверяет доступность, применяет последствия, выбирает следующий узел | текущий `DialogueChoice`; позже `ChoiceCondition` и `StateChange` |
| Переменные и флаги | Читает и изменяет сюжетное состояние | сначала методы `GameState`; позже `StoryStateService` без ломки фасада `GameState` |
| Отношения | Хранит очки/статусы отношений по стабильному ID персонажа | сначала существующие поля `GameState`; позже `RelationshipState` |
| Сохранения | Save/load, слоты, autosave/quicksave, метаданные, миграции | `SaveData`, `SaveManager` (уже есть) |
| Настройки | Громкость, экран, скорость текста, skip/auto и прочие пользовательские параметры | `GameSettings`, `SettingsManager` (уже есть) |
| Быстрое меню | Save, Load, History, Settings, Skip/Auto, возврат в меню | текущие панели `VNDialogueController`, `SaveLoadPanelController`, `SettingsPanelController`; отдельный контроллер добавлять только при росте UI |
| Аудио | Музыка, SFX, применение громкости | `AudioManager` (уже есть) |
| Валидация контента | Проверяет дубли ID, пустые тексты, отсутствующие переходы и ссылки | существующие Editor-валидаторы; расширять тестами, а не runtime-логикой |

## 2. Структура данных

### 2.1. Сцена

Исполняемая сцена — `DialogueSceneData`:

- `sceneId` — стабильный ID, не менять после использования в сохранениях;
- список упорядоченных `DialogueLine`;
- список доступных `DialogueChoice`;
- `defaultNextScene` — обычный переход без выбора;
- музыка и признак остановки музыки.

Правило: сохранение ссылается на `sceneId` и стабильный `lineId`, а не только на номер строки. Индекс строки оставляется как fallback для старых сохранений.

### 2.2. Диалог

`DialogueLine` хранит минимальный исполняемый набор:

- `lineId`;
- `speaker` или будущий `characterId`;
- текст;
- фон;
- спрайт персонажа;
- позиция персонажа;
- признак скрытия персонажа.

Для MVP этого достаточно. Отдельные эмоции, костюмы, эффекты и анимации добавлять позже как поля/ключи данных, не зашивая их в `VNDialogueController`.

### 2.3. Персонажи

На MVP персонаж задаётся ссылкой на `Sprite` в `DialogueLine`.

При появлении нескольких выражений и костюмов создать `CharacterData` в `Assets/HowIFall/Data/Characters/`:

- стабильный `characterId`;
- имя для UI;
- портрет/иконка;
- набор выражений или костюмов;
- настройки позиции и масштаба по умолчанию.

Сценарий будет ссылаться на `characterId` и ключ образа, но прямые ссылки на текущие спрайты должны продолжать работать для старых демо-сцен.

### 2.4. Выборы

Текущий `DialogueChoice` остаётся рабочим форматом MVP:

- текст варианта;
- текст результата;
- изменения существующих статов;
- следующая сцена.

Расширяемый формат должен содержать те же блоки в логике данных:

```text
Choice
  id
  text
  conditions[]     # требования по флагам/переменным/отношениям
  effects[]        # изменения состояния
  nextNodeId или nextSceneId
```

Условие должно быть видимым в сценарном Markdown: почему вариант доступен и какое последствие он даёт. Скрытые условия без документации не использовать.

### 2.5. Переменные и сюжетные флаги

На первом этапе сохраняем существующие явно типизированные поля `GameState` и `SaveData`: это проще проверять и не ломает текущие сохранения.

Набор, который требуется проекту:

- моральные/сюжетные оси: `humanity`, `corruption`, `lust`, `romance`, `self_control`, `suspicion`;
- системные значения: `demonic_points`, `money`, `chapter`, `day`, `investigation_progress`;
- булевы флаги: факт встречи, открытая улика, завершённая сцена, выбранный маршрут, доступный финал.

Когда явных полей станет много, добавить `StoryState` с сериализуемыми списками `IntValue`, `BoolFlag` и `StringValue`. Не использовать на раннем этапе обычный `Dictionary` как единственный формат: он неудобен для Unity `JsonUtility` и инспектора.

### 2.6. Отношения

Логическая модель:

```text
RelationshipState
  characterId
  score
  trust
  interest
  tags[]             # опционально, позже
```

Для MVP достаточно одного числового значения на отношение и существующих полей в `GameState`. Персонаж идентифицируется стабильным ID, а не отображаемым именем. Разные типы отношений (`trust`, `interest`, `respect`) добавлять только если они реально используются сценарием.

### 2.7. Сохранения

`SaveData` должен включать:

- версию формата;
- `sceneId`, `lineId` и fallback `lineIndex`;
- флаги, переменные и отношения;
- дату/время;
- номер слота и тип сохранения;
- заголовок, превью строки и путь к скриншоту.

Формат — JSON в `Application.persistentDataPath`. `SaveManager` уже отвечает за слоты, autosave/quicksave и миграцию; новые поля добавляются с повышением `version` и методом миграции. Сохранение пользовательских настроек остаётся отдельным от сохранения прохождения.

## 3. Минимальный MVP первого демо

### Обязательный результат

Одна рабочая VN-сцена в `VNPrototype`:

1. фон из уже имеющихся `Assets/HowIFall/Art/Backgrounds/`;
2. один персонаж из placeholder-ассетов;
3. 8–12 реплик с переходом по клику;
4. один осмысленный выбор с двумя последствиями или двумя короткими продолжениями;
5. изменение хотя бы одной переменной/отношения;
6. ручное сохранение и загрузка с восстановлением сцены и строки;
7. возврат в `MainMenu` без потери существующей логики.

### Не блокирует MVP

Backlog, полноценное quick menu, autosave, настройки, skip/auto, сложные условия, несколько маршрутов, локализация, QTE и мини-игры. Их архитектурные точки уже должны быть предусмотрены, но реализовывать их до проверки базового цикла не нужно.

### Критерий готовности MVP

Игрок запускает новую игру, читает сцену, делает выбор, сохраняется после выбора, закрывает/перезапускает сцену, загружает слот и продолжает с той же строки и тем же состоянием переменных.

## 4. Roadmap

### Этап 1 — базовый вертикальный срез

- Зафиксировать IDs сцены и строк в `docs/story/scenes/` и в `DialogueSceneData`.
- Проверить одну сцену на существующих фоне, персонаже и UI.
- Довести до стабильного состояния диалог, выбор, применение текущих stat-delta и переход.
- Проверить ручное сохранение/загрузку и восстановление по `sceneId` + `lineId`.
- Добавить/расширить Editor-проверки: пустые ID, дубли, битые ссылки, недостижимые переходы.

**Результат:** короткое запускаемое демо без новых сложных подсистем.

### Этап 2 — удобство прохождения и состояние истории

- Backlog всех показанных реплик.
- Quick menu: History, Save, Load, Settings, Skip/Auto, выход.
- Autosave/quicksave и несколько слотов с метаданными.
- Условия доступности выборов и булевы сюжетные флаги.
- Единая работа отношений и ключевых переменных через `GameState`.
- Переходы между несколькими `DialogueSceneData` без ручной логики в UI.

**Результат:** технически полноценный каркас прохождения одной главы с несколькими короткими ветками.

### Этап 3 — масштабирование контента

- Каталог `CharacterData` и ключи выражений/костюмов.
- Универсальные `StoryState`/`RelationshipState`, если число полей перестанет быть управляемым.
- Авторский формат Markdown как источник сценария и, при необходимости, импорт в ScriptableObject.
- Валидатор графа сцен: отсутствующие узлы, циклы без выхода, недостижимые ветки, конфликтующие IDs.
- Разделение общих сцен и route-сцен, route lock и ending flags.
- Только после стабильного графа: эффекты, QTE, интерактивные зоны, галерея и другие вторичные механики.

**Результат:** расширяемая основа для нескольких сюжетных веток без переписывания исполнителя диалогов.

## 5. Что намеренно не делаем сейчас

- Не меняем существующие сцены Unity, имена классов и игровую логику.
- Не переносим Ren’Py-код напрямую в C#.
- Не вводим отдельный DI-контейнер, ECS, сложную event-шину или универсальный визуальный редактор.
- Не создаём JSON-парсер до появления реальной потребности в массовом импорте.
- Не добавляем новые переменные и отношения только «на будущее»: сначала они должны быть нужны конкретной сцене или ветке.
